RCU — Read, Copy, Update

An interactive tour of the Linux kernel's read-mostly synchronization mechanism. Readers run lock-free and never block; updaters publish a new copy and defer reclamation until every pre-existing reader is done. Code samples come from Documentation/RCU/whatisRCU.rst in the kernel tree.

The five-piece core API

rcu_read_lock() / rcu_read_unlock() Mark an RCU read-side critical section. Never blocks, never spins — in non-preemptible kernels it compiles to nothing.
rcu_dereference(p) Fetch an RCU-protected pointer for safe dereferencing inside a read-side critical section. A volatile load plus (on Alpha) a memory barrier.
rcu_assign_pointer(p, v) Publish a new version: orders all initialization of v before the pointer store, so readers never see a half-built object.
synchronize_rcu() Block until a grace period elapses: every read-side critical section that started before the call has finished.
call_rcu(head, func) Non-blocking variant: invoke func(head) after a grace period, from softirq/process context.

Read flow interactive

The reader's entire job: enter the critical section, snapshot the pointer, use it, leave. No writes to shared memory, no waiting.

int foo_get_a(void){	int retval;	rcu_read_lock();	retval = rcu_dereference(gbl_foo)->a;	rcu_read_unlock();	return retval;}

Update flow — Read, Copy, Update interactive

The updater never modifies data in place while readers may be looking at it. It copies, modifies the copy, atomically publishes it, then waits a grace period before freeing the old version.

void foo_update_a(int new_a){	struct foo *new_fp, *old_fp;	new_fp = kmalloc(sizeof(*new_fp), GFP_KERNEL);	spin_lock(&foo_mutex);	old_fp = rcu_dereference_protected(gbl_foo,			lockdep_is_held(&foo_mutex));	*new_fp = *old_fp;	new_fp->a = new_a;	rcu_assign_pointer(gbl_foo, new_fp);	spin_unlock(&foo_mutex);	synchronize_rcu();	kfree(old_fp);}

Can't block? Replace the last two lines with call_rcu(&old_fp->rcu, foo_reclaim) — same grace-period guarantee, reclamation runs as a callback.

One updater, two readers interactive

The whole story on one timeline. Reader R1 enters its critical section before the update begins — it may hold a pointer to the old version, so the grace period must wait for it. Reader R2 enters after the update began — it can only ever see the new version, so it is never waited for.

rcu_dereference() vs rcu_dereference_protected()

Both fetch an RCU-protected pointer — the difference is what protects you while you use the result, and they encode that difference so tooling can verify it.

rcu_dereference(p) — reader side

For code inside rcu_read_lock()…rcu_read_unlock(). The pointer can change at any moment — an updater may publish a new version concurrently — so the macro:

  • does a volatile load, forbidding the compiler from reloading, speculating, or tearing it (and adds the barrier DEC Alpha needs);
  • pairs with the write barrier in rcu_assign_pointer(), so if you see the new pointer you also see its fully-initialized contents;
  • with CONFIG_PROVE_RCU, makes lockdep complain if called outside a read-side critical section.

The snapshot is valid only inside the enclosing section. From the doc — this is a bug:

rcu_read_lock();
p = rcu_dereference(head.next);
rcu_read_unlock();
x = p->address;	/* BUG!!! section over, p may be freed */
rcu_read_lock();
y = p->data;	/* BUG!!! a new section doesn't revive p */
rcu_read_unlock();

rcu_dereference_protected(p, c) — update side

For code that already holds the lock which serializes updates to this pointer. While you hold it, no other updater can swing the pointer — so:

  • no rcu_read_lock() needed and no read barriers — the compiler is even allowed to optimize accesses, which rcu_dereference() must forbid;
  • the second argument is a lockdep expression naming the protection. It is executable documentation: if the condition doesn't hold at runtime, lockdep emits a splat;
  • it says to the next reader of the code: "this pointer can't change under me, and here is why".
old_fp = rcu_dereference_protected(gbl_foo,
		lockdep_is_held(&foo_mutex));

Rule of thumb: reading concurrently → rcu_dereference() inside a section. Updating under the update lock → rcu_dereference_protected() with the matching lockdep_is_held(). (In this tree: net/core/gen_estimator.c uses rcu_dereference_protected(*rate_est, 1) while holding the qdisc lock — the constant 1 says "trust me", used where the protecting lock is the caller's and can't be named in a lockdep expression.)

Why foo_mutex? Who holds it? interactive

RCU protects readers from updaters — it does nothing to protect updaters from each other. rcu_assign_pointer() is just a store with a barrier; two concurrent updaters doing read-copy-update on the same pointer will race. The mutex serializes them. Only updaters take it — readers never touch it, which is exactly why reads keep scaling.

With foo_mutex (correct)

  1. U1: spin_lock(&foo_mutex)
  2. U1: reads gbl_foo → A, copies to B, sets .a = 42
  3. U1: rcu_assign_pointer(gbl_foo, B), unlock, GP, kfree(A)
  4. U2: spin_lock(&foo_mutex) (was blocked until now)
  5. U2: reads gbl_foo → B, copies to C, sets .b = 'x'
  6. U2: publishes C, unlock, GP, kfree(B)

Final version C has both updates (.a = 42 and .b = 'x'); every version freed exactly once.

Without the mutex (broken)

  1. U1: reads gbl_foo → A, copies to B, sets .a = 42
  2. U2: reads gbl_foo → A too, copies to C, sets .b = 'x'
  3. U1: rcu_assign_pointer(gbl_foo, B)
  4. U2: rcu_assign_pointer(gbl_foo, C) — U1's .a = 42 is silently lost (C was copied from A, not B)
  5. U1: synchronize_rcu(); kfree(A)
  6. U2: synchronize_rcu(); kfree(A) — double free of A, and B leaks

Two classic corruption bugs from one missing lock: a lost update and a double-free. Nothing about RCU prevents this — serializing updaters is explicitly the caller's job ("Use some solid design, such as locks, to keep concurrent updates from interfering with each other").

Who holds what, at a glance: readers hold only rcu_read_lock() (free, never blocks); updaters hold foo_mutex across read pointer → copy → modify → rcu_assign_pointer(), and may drop it before synchronize_rcu() — the grace-period wait needs no lock, and holding a mutex across it just lengthens the critical section. In net/core/gen_estimator.c below, the qdisc spinlock plays the role of foo_mutex: estimator create/replace runs under it, while the gen_estimator_read() fast path never takes it.

What exactly does a grace period wait for? animation

synchronize_rcu() waits only for read-side critical sections that are already running when it is called — not ones that begin afterwards. Straight from the document:

	CPU 0                  CPU 1                 CPU 2
	----------------- ------------------------- ---------------
	1.  rcu_read_lock()
	2.                    enters synchronize_rcu()
	3.                                               rcu_read_lock()
	4.  rcu_read_unlock()
	5.                     exits synchronize_rcu()
	6.                                              rcu_read_unlock()

The same pattern in real kernel code

A small, self-contained example: the network packet-rate estimator, net/core/gen_estimator.c (~280 lines). Every qdisc can have a struct net_rate_estimator __rcu * attached. The fast path reads it constantly; reconfiguration swaps it. It is the foo_get_a() / foo_update_a() pattern, verbatim:

/* reader — gen_estimator_read() */
rcu_read_lock();
est = rcu_dereference(*rate_est);
if (!est) {
	rcu_read_unlock();
	return false;
}

do {
	seq = read_seqcount_begin(&est->seq);
	sample->bps = est->avbps >> 8;
	sample->pps = est->avpps >> 8;
} while (read_seqcount_retry(&est->seq, seq));

rcu_read_unlock();
return true;

RCU guarantees est stays allocated; the inner seqcount loop handles the orthogonal problem of reading two fields consistently while the estimator timer updates them.

/* updater — gen_new_estimator() */
if (lock)
	spin_lock_bh(lock);   /* the "foo_mutex" */
old = rcu_dereference_protected(*rate_est, 1);
if (old) {
	timer_delete_sync(&old->timer);
	est->avbps = old->avbps;   /* the "copy" */
	est->avpps = old->avpps;
}
...
rcu_assign_pointer(*rate_est, est); /* publish */
if (lock)
	spin_unlock_bh(lock);
if (old)
	kfree_rcu(old, rcu);  /* free after GP */

Same five moves: lock out other updaters → fetch current with rcu_dereference_protected() → build the replacement → publish with rcu_assign_pointer() → defer the free past a grace period (kfree_rcu() instead of synchronize_rcu(); kfree(), since this path must not block).
