Shadow Stack — catching return-address hijacking

A function's return address lives on the same stack as its local buffers. Overflow a buffer and you overwrite that address — the classic stack buffer overflow. A shadow stack keeps a second, separate copy of every return address and checks it before returning. Below is the whole idea in ~10 lines of real x86-64 — step through it, then flip on the attack.

1 · The simplest possible defense

You don't need CPU support. Reserve one callee-saved register as a shadow stack pointer — here %r15 — pointing into a separate memory region the overflow can't reach. Two snippets do everything:

Prologue (right after entry, the call already pushed the return address to [rsp]):

# copy the real return address into the shadow region
mov  (%rsp), %rax
sub  $8, %r15
mov  %rax, (%r15)     # trusted copy — attacker can't see r15's region

Epilogue (replace the bare ret):

mov  (%rsp), %rax     # what's on the main stack now (maybe corrupted)
mov  (%r15), %rcx     # what we saved (trusted)
add  $8, %r15
cmp  %rcx, %rax
jne  __ss_abort       # mismatch ⇒ someone rewrote the return address
ret

That's a software shadow stack. Compilers automate it (-fsanitize=shadow-call-stack on ARM64, -mshstk + Intel CET hardware on x86), but the mechanism is exactly these lines.

./demo AAAAAAAAAAAAAAAAAAAAAAAABBBBBBBB   # attack

-fno-stack-protector is required so the compiler's own canary doesn't steal the show — we want to watch the shadow stack catch it. -no-pie keeps addresses fixed so the demo is reproducible.

3 · Why the shadow copy is safe

The overflow walks upward from a local buffer through saved registers into the return slot — all on the main stack. The shadow region sits at a completely different address held only in %r15, which never gets spilled to the vulnerable frame. The attacker can smash [rsp] all day; (%r15) still holds the truth, and cmp notices the two disagree.

4 · Real software shadow stacks in the wild

The %r15 trick above is the teaching version. Here are the production systems that ship the same idea — a separate, protected copy of return addresses — in software:

LLVM / Clang ShadowCallStack — -fsanitize=shadow-call-stack. Production on AArch64, where it reserves register x18 as the shadow stack pointer (exactly the %r15 role). The earlier x86-64 version was removed: on x86 the pointer had to live in a general register an attacker could find and the return address is pushed by call onto the normal stack anyway, so it couldn't be made robust — x86 was handed to hardware CET instead. Shipped broadly in Android (platform binaries and the kernel).

SafeStack — -fsanitize=safe-stack. Not a return-address copy but a close cousin: it splits every frame into a safe stack (return address, spilled registers, anything not address-taken) held at a hidden location, and an unsafe stack (arrays and address-taken locals) that an overflow can only trash without reaching the return address.

grsecurity / PaX RAP — Return Address Protection in the grsecurity kernel patch. Guards return addresses with a cryptographic/cookie scheme rather than a plain second stack; long predates the mainline hardware options.

Microsoft RFG — Return Flow Guard was Microsoft's software shadow stack for Windows. It was abandoned before shipping once red-teams showed the thread-setup window was racy; Microsoft waited for Intel CET's hardware version instead.

Go takes a different road entirely: goroutine stacks are managed and copied by the runtime, and safe Go has no way to overflow a buffer into a return address, so it needs no shadow stack at all. The problem is designed out rather than defended.

Notice the pattern: on x86-64 the software approaches all struggled with the same weakness this demo glosses over — the shadow pointer lives in a register or ordinary memory the attacker shares. That's precisely why the hardware shadow stack exists: the CPU holds the pointer and maps the copy on pages a normal store can't touch.
