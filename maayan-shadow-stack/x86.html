x86-64: clang has no software shadow stack — so the CPU keeps it

The AArch64 page showed clang emitting an explicit shadow push/pop around every call. On x86-64 that instrumentation doesn't exist: -fsanitize=shadow-call-stack is silently accepted but emits nothing. The return-address defense on x86 is Intel CET — a hardware shadow stack the compiler only has to opt into with endbr64. Everything below was compiled and run on a real x86-64 Linux box (CentOS 9, clang 20) over SSH.

1 · The same program, on x86-64 calls.c

Identical call chain — main → compute → add, then compute → square — but frame() now reads %rsp directly. Compiled and run natively on the x86 host:

static void frame(const char *fn) {
    void *rbp = __builtin_frame_address(0);
    void *ret = __builtin_return_address(0);
    void *rsp; __asm__ volatile("mov %%rsp, %0" : "=r"(rsp));
    printf("%-8s rbp=%p  rsp=%p  ret=%p\n", fn, rbp, rsp, ret);
}
$ ssh home 'clang -O0 -fno-omit-frame-pointer calls.c -o calls && ./calls'
main     rbp=0x7ffff9005810  rsp=0x7ffff90057f0  ret=0x40123e
compute  rbp=0x7ffff90057f0  rsp=0x7ffff90057d0  ret=0x4011fd
add      rbp=0x7ffff90057d0  rsp=0x7ffff90057b0  ret=0x40114d
square   rbp=0x7ffff90057d0  rsp=0x7ffff90057b0  ret=0x4011ca
= 49

Same shape as AArch64: 0x20 per frame, and add/square sharing a frame as siblings. The one x86 difference that matters here — the return address ret is pushed onto the main stack by call (it sits just above the saved rbp), whereas AArch64 keeps it in the x30 register until a non-leaf spills it. That stack-resident return address is exactly what an overflow reaches.

2 · Why there's no clang shadow stack on x86 verified

Ask clang for ShadowCallStack on x86-64 and it takes the flag without complaint — but the generated code is byte-for-byte identical to the plain build:

# both produce the same assembly for compute()
clang -O1 -S compute.c
clang -O1 -fsanitize=shadow-call-stack -S compute.c
# diff → no difference. It is a silent no-op.

The x86-64 SCS backend was removed years ago: with the return address on the stack and the shadow pointer forced into a general register an attacker can locate and spill, it couldn't be made robust. x86 was handed to hardware instead.

What you use instead is -fcf-protection=full, which makes the binary Intel-CET-ready. In the function body that adds exactly one thing — an endbr64 landing pad — and no shadow push/pop, because the CPU does that itself on call/ret:

compute:
    endbr64                # CET landing pad
    pushq  %rbp
    movq   %rsp, %rbp
    callq  add            # CPU pushes ret to SSP too
    movl   %eax, %edi
    popq   %rbp
    jmp    square         # tail call

Compare the AArch64 page: there clang emitted str x30, [x18] / ldr x30, [x18,#-8]! by hand. Here that work is invisible — it's the silicon.

3 · The software option that does work on x86: SafeStack -fsanitize=safe-stack

x86 isn't defenseless in software — it just doesn't copy return addresses. SafeStack instead moves the dangerous data away: any local whose address is taken (a buffer you can overflow) goes on a separate "unsafe" stack, while return addresses and spills stay on the normal stack an overflow can no longer reach. Here's the real prologue clang emits for a greet() that strcpys into char buf[16]:

greet:
    pushq %rbp
    movq  %rsp, %rbp
    ...
    movq  __safestack_unsafe_stack_ptr@GOTTPOFF(%rip), %r14
    movq  %fs:(%r14), %r15        # load unsafe SP from TLS
    leaq  -16(%r15), %rbx      # carve 16 bytes for buf[16]
    movq  %rbx, %fs:(%r14)     # commit the unsafe SP
    movq  %rbx, %rdi
    callq strcpy               # buf lives on the UNSAFE stack
    ...
    movq  %r15, %fs:(%r14)     # restore unsafe SP
    popq  %rbp
    retq                       # return addr was never near buf

Read it top to bottom: the unsafe stack pointer lives in thread-local storage (%fs:), the 16-byte buffer is allocated there via leaq -16(%r15), and strcpy writes into that region. Meanwhile retq still pops its return address from the ordinary stack — which the buffer overflow can no longer touch, because buf isn't next to it anymore.

It's a different bet than a shadow stack: rather than keep a second copy of the return address and check it, SafeStack makes sure the overflow and the return address never share a neighborhood. Ships in clang for x86-64 today.

Reproduce on any x86-64 Linux box with clang:

# live addresses
clang -O0 -fno-omit-frame-pointer calls.c -o calls && ./calls
# CET-ready assembly (note endbr64, no shadow push)
clang -O1 -fcf-protection=full -S calls.c
# SafeStack prologue
clang -O1 -fsanitize=safe-stack -S greet.c
