C++ exceptions vs the shadow stack

A throw doesn't return one frame at a time — the unwinder rips past many frames at once to reach the matching catch. But every one of those skipped frames also pushed a return address onto the shadow stack. If the shadow stack isn't unwound in lockstep, its pointer is left dangling and the next ordinary ret faults. Here's how clang solves that on both architectures — real output, x86-64 run over SSH, AArch64 cross-compiled.

1 · A throw across four frames ex.cpp

main calls middle, which recurses deep(3) → deep(0), and the innermost frame throws. The catch is all the way back in main — so the unwinder must discard five frames in one shot.

struct Boom { int code; };
void deep(int n) {
    if (n == 0) throw Boom{42};   // innermost frame throws
    printf("deep(%d)\n", n);
    deep(n - 1);
}
void middle() { deep(3); }
int main() {
    try { middle(); }
    catch (const Boom& b) { printf("caught %d\n", b.code); }
}

Built on the x86-64 host both ways — plain, and with the CET shadow stack — it unwinds cleanly either way:

$ ssh home 'clang++ -O1 ex.cpp -o ex && ./ex'
  deep(3) … deep(2) … deep(1)
caught Boom code=42 — unwound cleanly

$ ssh home 'clang++ -O1 -fcf-protection=full ex.cpp -o ex_cet && ./ex_cet'
  deep(3) … deep(2) … deep(1)
caught Boom code=42 — unwound cleanly   # shadow stack stayed consistent

Same result — which is the whole point. The machinery that keeps the shadow stack consistent through the unwind is invisible at the C++ level. Below is where it actually lives, and it's in a different place on each architecture.

2 · AArch64 — the rule is baked into the code ShadowCallStack

With -fsanitize=shadow-call-stack, clang instruments deep() with the usual shadow push — but it also emits a DWARF unwind rule for x18. Those two lines (highlighted) are the entire difference from the plain build:

_Z4deepi:                    # deep(int)
    str  x30, [x18], #8      # push ret → shadow stack
    .cfi_escape 0x16,0x12,0x02,0x82,0x78
    stp  x29, x30, [sp, #-32]!
    mov  x29, sp
    ...
    bl   __cxa_allocate_exception
    bl   __cxa_throw          # the throw

That .cfi_escape decodes to a DW_CFA_val_expression for register 18:

0x16  DW_CFA_val_expression
0x12  register 18  (x18)
0x02  expression length = 2
0x82  DW_OP_breg18   # "value of x18 plus…"
0x78  SLEB128 = -8

Read it as a sentence: to unwind one frame, set x18 = x18 − 8 — pop exactly one 8-byte shadow slot. The unwind tables carry this rule for every instrumented frame, so when libunwind walks past deep(0) … middle, it subtracts 8 from x18 five times and lands with the shadow pointer perfectly aligned to main's frame. No runtime shadow-stack code needed — it's static metadata.

3 · x86-64 — the rule lives in the unwinder Intel CET

On x86 the shadow stack is the CPU's, and -fcf-protection=full adds no per-frame shadow instructions — just an endbr64 landing pad. So there's no CFI rule to carry. Instead the runtime unwinder itself drives the shadow stack. The binary is marked for CET:

$ readelf -n ./ex_cet
  Properties: x86 feature: IBT, SHSTK

…and the shadow-stack logic is right there inside libgcc_s, the unwinder that __cxa_throw calls into:

$ objdump -d /lib64/libgcc_s.so.1 \
    | grep -oE 'incsspq|rdsspq' | sort | uniq -c
      8 incsspq     # pop N shadow slots
      4 rdsspq      # read current SSP

When the unwinder restores a context that skips several frames, it computes how many return addresses those frames put on the shadow stack and executes incsspq to advance SSP past exactly that many — the dynamic equivalent of AArch64's static x18 −= 8 rule. rdsspq reads SSP so it knows where it is. This is why a CET binary can throw across frames without a spurious #CP fault: the unwinder pops the shadow stack for you.

(On this particular host /proc/cpuinfo has no user_shstk, so CET isn't hardware-live — but the binary is CET-marked and the unwinder path is compiled in, which is what the counts above prove.)
