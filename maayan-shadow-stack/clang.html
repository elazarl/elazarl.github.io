1 · The program calls.c

Four functions in a chain: main → compute → add, then compute → square. Each one prints its own live frame — x29 (the frame pointer), sp, and x30 (the return address it was given).

static void frame(const char *fn) {
    void *fp  = __builtin_frame_address(0);   // x29
    void *ret = __builtin_return_address(0);  // x30
    void *sp; __asm__ volatile("mov %0, sp" : "=r"(sp));
    printf("%-8s x29=%p  sp=%p  x30=%p\n", fn, fp, sp, ret);
}
int add(int a, int b)     { frame("add");     return a + b; }
int square(int n)         { frame("square");  return n * n; }
int compute(int x, int y) { frame("compute"); return square(add(x, y)); }
int main(void)            { frame("main");    printf("= %d\n", compute(3, 4)); }

Compiled and run natively (clang -O0 -fno-omit-frame-pointer), it prints these real addresses — the numbers the stepper below uses:

$ ./calls
main     x29=0x16d7095f0  sp=0x16d7095b0  x30=0x1026f459c
compute  x29=0x16d7095d0  sp=0x16d709590  x30=0x1026f454c
add      x29=0x16d7095b0  sp=0x16d709570  x30=0x1026f4480
square   x29=0x16d7095b0  sp=0x16d709570  x30=0x1026f4514
= 49

Two things to notice in the raw numbers, before any picture: each nested call drops x29 by exactly 0x20 (32 bytes per frame), and add and square report the same x29/sp — they're siblings called one after the other, so square reuses the exact stack slot add just gave back.

2 · What ShadowCallStack actually emitted clang -S

Same source, recompiled with the sanitizer on:

clang --target=aarch64-linux-gnu -O1 -fno-omit-frame-pointer \
      -fsanitize=shadow-call-stack -ffixed-x18 -S calls.c

compute() is a non-leaf (it calls other functions), so it gets instrumented. The two highlighted lines are the entire difference from the plain build:

compute:
    str  x30, [x18], #8        # push x30 → shadow, x18 += 8
    stp  x29, x30, [sp, #-16]!  # normal frame on main stack
    mov  x29, sp               # set frame pointer
    bl   add                   # compute → add(x, y)
    ldp  x29, x30, [sp], #16   # restore from main stack
    ldr  x30, [x18, #-8]!      # x18 -= 8, reload TRUSTED x30
    b    square                # tail-call square(...)

add() is a leaf — it calls nothing, so x30 never gets spilled to memory and there's nothing to protect. clang emits no shadow instructions at all:

add:
    add  w0, w1, w0
    ret

This is the whole mechanism, and note what it is not: there's no cmp, no branch-to-abort. On return, ldr x30, [x18, #-8]! simply overwrites x30 with the trusted copy from the shadow stack. Whatever an overflow wrote into the main-stack return slot is discarded — the function returns to the address the shadow stack remembers, full stop.

-ffixed-x18 reserves register x18 as the dedicated shadow-stack pointer so nothing else clobbers it — the compiler's version of the %r15 we picked by hand on the software page.

4 · The AArch64 ↔ x86-64 map, and how to reproduce

x29Frame pointer — base of the current frame. The x86-64 rbp.
spStack pointer — current top. The x86-64 rsp.
x30 (LR)Link register — holds the return address. On x86-64 that address lives on the stack; on AArch64 bl puts it in a register, which is why leaves needn't touch memory.
x18Reserved as the shadow-stack pointer under SCS. The hand-rolled %r15, promoted to an ABI contract.

Everything on this page reproduces with stock clang:

# 1 · live addresses (native, no SCS runtime needed)
clang -O0 -fno-omit-frame-pointer -o calls calls.c && ./calls

# 2 · the instrumented assembly
clang --target=aarch64-linux-gnu -O1 -fno-omit-frame-pointer \
      -fsanitize=shadow-call-stack -ffixed-x18 -S calls.c

On real Android/AArch64 Linux the same binary links against a runtime that allocates the guarded shadow region and reserves x18 process-wide — then the str/ldr pair above is live protection, not just a sketch.
