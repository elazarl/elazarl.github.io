Hardware Shadow Stack — the CPU keeps the copy

On the software page the function carried eight extra instructions to maintain a shadow copy of its return address. With Intel CET (CET) or ARM GCS, that work moves into silicon: call pushes the return address to a second, hardware-protected stack automatically, and ret checks it. The function's own code is unchanged — the same plain greet(), zero instrumentation.

1 · What the hardware actually does

Once CET shadow stacks are enabled, every call becomes an implicit dual push and every ret an implicit compare:

  • call → push return address to the main stack and to SSP.
  • ret → pop from both. If they differ, the CPU raises a #CP (Control-Protection) fault → the kernel delivers SIGSEGV.

The shadow pages carry a special page-table encoding: normal writes to them fault, so an overflow can't quietly rewrite the copy the way it rewrites the main stack. That's the guarantee %r15 only approximated in software.

2 · The instructions you can use

The push/check are automatic, but privileged and setup code needs to touch the shadow stack explicitly:

rdsspq %rax        # read current SSP
incsspq $1         # pop N slots (e.g. longjmp/unwind)
wrssq  %rax,(%rcx) # write to shadow stack (needs WRSS enabled)
rstorssp (%rax)    # switch to a saved shadow stack (context switch)
saveprevssp       # save the previous SSP token
endbr64            # CET IBT landing pad — separate feature, not the shadow stack

Enable bits live in IA32_U_CET / IA32_S_CET MSRs, gated by CR4.CET. Per-thread SSP for ring 3 comes from IA32_PL3_SSP.

3 · Turning it on

You compile for it and the OS arms it per-process:

# GCC/Clang: emit CET-compatible code
gcc -fcf-protection=full -O2 prog.c -o prog

# Linux enables it via arch_prctl(ARCH_SHSTK_ENABLE)
# glibc does this automatically when the binary + CPU support it.
# Windows: "Hardware-enforced Stack Protection" (opt-in per app).

Hardware: Intel from Tiger Lake (11th-gen) and AMD from Zen 3. If either the CPU or the loaded libraries lack CET, the loader silently falls back to no shadow stack — a whole process must be CET-clean, because one legacy library that does unusual stack tricks would fault.

4 · ARM's two answers

PAC (Pointer Authentication, ARMv8.3-A) came first and is not a shadow stack. It signs the return address with a cryptographic MAC packed into the pointer's unused top bits, keyed by a secret + the stack pointer:

paciasp   # sign LR using SP as modifier (function entry)
...
autiasp   # authenticate LR before return; corrupt ⇒ fault
ret

GCS (Guarded Control Stack, Armv9.4-A / FEAT_GCS) is the real shadow stack: a hardware-managed second stack via GCSPR_EL0, with gcspushm / gcspopm and stack-switch ops gcsss1/gcsss2. It supersedes PAC-for-returns with the same guarantee Intel CET gives.

5 · Why bother with hardware

The software version cost real instructions in every prologue and epilogue, and burned a register. Hardware makes the check nearly free, protects the copy with page permissions software can't forge, and can't be skipped by jumping past the check — the ret itself is the check.
