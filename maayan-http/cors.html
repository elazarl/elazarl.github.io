CORS — how one site is allowed to read another

Cross-Origin Resource Sharing. By default the browser lets your JavaScript send a request anywhere but not read the answer from another origin. CORS is the mechanism by which the server says "this origin may read my response" — and the browser then, and only then, hands it over.

The one idea

CORS is not a lock the browser adds. It is a relaxation of a lock that was always there: the Same-Origin Policy. Without CORS headers, cross-origin reads are blocked. With them, the server opts in — per origin, per method, per header.

Who decides: the server. Who enforces: the browser. Nothing else. curl, your backend, a mobile app and a Python script all ignore CORS entirely — they were never bound by the Same-Origin Policy to begin with.

What counts as "another origin"

An origin is scheme://host:port. All three must match exactly — no cleverness, no "same company" logic:

Compared to https://app.example.comSame origin?Why
https://app.example.com/other/pathYesPath is not part of the origin
http://app.example.comNoDifferent scheme
https://api.example.comNoDifferent host — a subdomain is a different origin
https://app.example.com:8443NoDifferent port

This is why a frontend on app.example.com talking to its own API on api.example.com needs CORS. Same owner, same certificate, same team — still cross-origin.

How SOP applies: sending is allowed, reading is not

The Same-Origin Policy is often summarized as "you can't talk to other sites". That is wrong, and the difference is the whole point:

  • Sending is old and unrestricted. <img src>, <script src>, <link>, <form> and stylesheets have been reaching across origins since 1995. The web is built on it.
  • Reading is what's guarded. Your JS cannot see the response body, status or most headers of a cross-origin request unless the server allows it.

That asymmetry is exactly the hole CSRF lives in: the attacker doesn't need to read anything, only to cause a state change. CORS closes the reading half, not the sending half — so CORS is not a CSRF defense, and never was.

Concretely, with fetch() from https://app.example.com to https://api.other.com/me: the request does leave your machine, the server does process it and does answer. Then the browser inspects the response, finds no permission for your origin, throws away the body and rejects the promise. The "CORS error" is a post-hoc refusal to show you what already happened.

The simple case — one request, one header

Browser adds Origin to every cross-origin request. It is not optional and JS cannot forge it:

GET /rates HTTP/1.1 Host: api.other.com Origin: https://app.example.com ← set by the browser, always truthful

The server answers with the permission slip:

HTTP/1.1 200 OK Access-Control-Allow-Origin: https://app.example.com Content-Type: application/json {"USD":3.71}

Header matches the asking origin → the browser hands the JSON to your JS. Header missing or different → the response is discarded, and only a console message survives.

Access-Control-Allow-Origin: * means "any origin may read this". Correct for genuinely public data (fonts, public price feeds, CDN assets). Wrong the moment the response depends on who asked — see credentials below, where the browser refuses * outright.

The preflight — asking permission before doing anything

A plain <form> could always POST cross-site, so servers have always had to cope with that. But a PUT, a DELETE, a custom header like X-Api-Key or a JSON content type were never possible from old HTML. Servers were written assuming they could not arrive cross-origin. So before sending one, the browser asks first:

OPTIONS /orders/42 HTTP/1.1 ← the preflight, sent by the browser on its own Host: api.example.com Origin: https://app.example.com Access-Control-Request-Method: DELETE Access-Control-Request-Headers: authorization, content-type
HTTP/1.1 204 No Content Access-Control-Allow-Origin: https://app.example.com Access-Control-Allow-Methods: GET, POST, DELETE Access-Control-Allow-Headers: authorization, content-type Access-Control-Max-Age: 86400 ← cache this answer 24h, skip the extra round-trip

Only after a satisfying preflight does the real DELETE get sent. If the preflight fails, the actual request never leaves the browser — the one case where CORS truly prevents the request rather than hiding the answer.

No preflight needed ("simple request") for GET/HEAD/POST with only CORS-safelisted headers and a Content-Type of application/x-www-form-urlencoded, multipart/form-data or text/plain. Note what's absent: application/json. Sending JSON is enough to trigger a preflight — that surprise is most people's first CORS bug.

Credentials — where cookies come in

By default fetch() sends no cookies cross-origin and ignores Set-Cookie in the reply. To use the session you must ask explicitly:

// on https://app.example.com fetch("https://api.example.com/me", { credentials: "include" }) // XHR equivalent: xhr.withCredentials = true

Now the request carries the cookie — and the server must answer with a stricter pair of headers:

HTTP/1.1 200 OK Access-Control-Allow-Origin: https://app.example.com ← exact origin. `*` is rejected here Access-Control-Allow-Credentials: true Vary: Origin ← or a cache serves origin A's permission slip to origin B

Three rules that trip everyone:

  • * is banned with credentials. The browser refuses the response even though the server said yes. You must echo the exact Origin — which means keeping an allowlist, because echoing whatever arrives is the same as trusting every site on the internet.
  • The cookie must also be allowed to travel. CORS and SameSite are independent gates. With the modern default SameSite=Lax, the cookie is not attached cross-site at all — no CORS header can override that. Cross-site sessions need SameSite=None; Secure, which re-opens the CSRF door and puts you back on tokens.
  • Credentials means all ambient authority, not just cookies: Authorization set by the browser, TLS client certs. A bearer token you attach by hand is just a header — no credentials flag needed, but it does force a preflight.

Why the browser is this paranoid: if evil.com could send credentialed requests and read the replies, the Same-Origin Policy would be gone. It would fetch("https://mail.example.com/inbox", {credentials:"include"}) and read your mail with your own cookie. Allow-Credentials: true is a server explicitly saying "this named origin is part of my trust boundary."

Reading response headers

Even on an allowed response, JS sees only a short safelist of headers. Anything else — pagination counts, a request id, Location — must be published:

Access-Control-Expose-Headers: X-Total-Count, X-Request-Id

Without this, res.headers.get("X-Total-Count") returns null while the header is plainly visible in DevTools. DevTools shows the wire; JS sees the filtered view.

A real example — why CORS earns its keep

You run a bike-rental service. Frontend is a static React bundle on a CDN at https://app.bikes.com; the API is a separate deployment at https://api.bikes.com; you also sell an embeddable "bikes near you" widget that partner hotels drop into their own sites.

Without CORS your only options are the bad old ones: proxy every API call through the CDN origin (a second hop, extra latency, defeats deploying the API independently), or serve JSON through <script> tags as JSONP — which is GET-only and hands the remote origin full script execution in your page.

One deployment, three trust levels, expressed in response headers instead of network topology. That is the useful part: the API decides who may read it, and can change its mind with a config edit.

What CORS is not

  • Not access control for your server. A blocked read still ran your code and touched your DB. Attackers use curl. Authentication and authorization are still entirely your job.
  • Not a CSRF defense. Simple requests need no permission to be sent. Use SameSite and tokens.
  • Not something the client can fix. No fetch option, no header from JS, no frontend library grants you access — only the server's response can. A "CORS proxy" works by being a different server that adds the header.
  • Not about the network. localhost:3000 → localhost:8080 is cross-origin. Same machine, same process tree, different port.

Rule of thumb: public and user-agnostic data → *. Anything tied to a session → exact origin from an allowlist, Allow-Credentials: true, Vary: Origin, and CSRF protection on top. Never reflect an arbitrary Origin back with credentials enabled — that is a one-line rewrite of the Same-Origin Policy into "everyone is trusted".

CORS reads like a restriction and behaves like a permission: the default was always "you may knock, you may not look inside". CORS is the server holding the door open for named guests. See also CSRF — the attack that lives in the knocking half — and HTTP/1.1.
