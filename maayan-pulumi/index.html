Pulumi — how a program becomes cloud infrastructure

Instead of clicking around a cloud console, you describe the servers, databases and networks you want in a real programming language. Pulumi runs that program, works out the difference between what you asked for and what already exists in the cloud, and makes exactly the API calls needed to close the gap. This page explains the machinery, then walks a concrete example: deploying a Node.js backend to Google Cloud Run.

The big picture · what happens when you run Pulumi

Pulumi is infrastructure as code. Your program doesn't do the work itself — it declares the resources you want. The Pulumi engine reads those declarations, talks to a provider plugin for your cloud, and turns them into real API calls.

  A["Your program
(TypeScript / Python / Go)"] --> B["Language host

  B -- "registers resources" --> C["Deployment engine
builds a desired-state graph"]
  C -- "compares with" --> D[("State

real resources"]
  F -- "actual results" --> D

Your code only names what should exist. The engine figures out the how — the order, the dependencies, and the minimal set of changes.

The one idea that matters · desired state vs. actual state

Every time you run Pulumi it does the same three things: read your program to get the desired state, read the state file to get the last-known actual state, and compute a diff. Only the diff is executed — this is what makes re-running safe and idempotent.

flowchart TB
  P["Desired state
(from your code)"] --> DIFF{"Compare"}
  S[("Actual state
(from state file)")] --> DIFF
  DIFF -- "in code, not in cloud" --> CR["➕ Create"]
  DIFF -- "changed" --> UP["✏️ Update"]
  DIFF -- "in cloud, not in code" --> DEL["🗑️ Delete"]
  DIFF -- "identical" --> NO["✓ No change"]

The verbs you actually type

pulumi preview shows the diff, changes nothing.
pulumi up shows the diff, then applies it after you confirm.
pulumi refresh re-reads the cloud to catch drift.
pulumi destroy deletes everything the stack created.

Because the engine always converges toward your code, your program is the single source of truth. Delete a resource from the code and the next up deletes it from the cloud.

The vocabulary · six words that cover almost everything

Resource

One thing in the cloud — a Cloud Run service, a bucket, a database. You create it by constructing an object: new gcp.storage.Bucket(...).

Provider

The plugin that knows a cloud's API. @pulumi/gcp maps your resource objects to Google Cloud calls; there are providers for AWS, Azure, Kubernetes and ~150 more.

Stack

One independent instance of your program — dev, staging, prod. Same code, different config and its own state.

State & backend

The record of what Pulumi created, stored in a backend (Pulumi Cloud, an S3/GCS bucket, or a local file).

Inputs & Outputs

An Output is a value known only after a resource exists (like a URL). Feed one resource's output into another's input and Pulumi learns the dependency automatically.

Program

Your whole entry file. It runs top-to-bottom once per up, registering every resource. Loops, conditionals and functions are all fair game — it's real code.

Why a real language instead of YAML?

Static config files (YAML, JSON) can't express "make 3 of these", "only in production", or "derive this name from that ID" without bolting on a templating layer. A real language gives you loops, variables, functions, types and your editor's autocomplete for free. Pulumi still supports YAML for simple cases — but the point is you're not forced into it. The trade-off: with real code you can also write real bugs, so most teams keep infrastructure programs small and boring.

Example · deploying a Node.js backend to Cloud Run

Cloud Run runs a container and scales it up and down for you — including scaling to zero when idle. To deploy a Node.js API we need four resources, and they have a natural order. Here is what a single pulumi up actually does:

sequenceDiagram
  participant You as pulumi up
  participant Eng as Engine
  participant AR as Artifact Registry
  participant Run as Cloud Run
  participant IAM as IAM
  You->>Eng: read program, build graph
  Eng->>AR: create Docker repository
  Eng->>AR: build ./app image & push it
  AR-->>Eng: image digest
  Eng->>Run: create service from that image
  Run-->>Eng: service URL
  Eng->>IAM: allow allUsers to invoke
  Eng-->>You: export url = https://api-xxxx.run.app

Notice the arrows carry data: the image's digest flows into the service, and the service's URL flows back to you as an output. Pulumi derives the order from that data flow — you never write it explicitly.

The code · click any line to see what it does

import * as gcp from "@pulumi/gcp";import * as docker from "@pulumi/docker";import * as pulumi from "@pulumi/pulumi"; const location = "us-central1"; // 1. somewhere to keep the container imageconst repo = new gcp.artifactregistry.Repository("backend", { repositoryId: "backend", format: "DOCKER", location,}); // 2. build ./app into an image and push itconst registry = pulumi.interpolate`${location}-docker.pkg.dev`;const image = new docker.Image("api-img", { imageName: pulumi.interpolate`${registry}/${gcp.config.project}/backend/api`, build: { context: "./app", platform: "linux/amd64" },}); // 3. the Cloud Run service that runs the containerconst service = new gcp.cloudrunv2.Service("api", { location, template: { containers: [{ image: image.imageName, ports: [{ containerPort: 8080 }], resources: { limits: { cpu: "1", memory: "512Mi" } }, }], scaling: { minInstanceCount: 0, maxInstanceCount: 10 }, },}); // 4. let anyone on the internet call itnew gcp.cloudrunv2.ServiceIamMember("public", { name: service.name, location, role: "roles/run.invoker", member: "allUsers",}); // 5. print the public URL when doneexport const url = service.uri;

Click any line of code

Four resources — a repository, an image, a service and an IAM grant — plus one exported output. Click a line to see what it declares and how Pulumi uses it. Notice you never write "wait for the image before the service": passing image.imageName into the service is enough for Pulumi to order them.
What's in ./app — the Node.js server itself

The container just needs to listen on the port Cloud Run injects via $PORT (it's 8080 here). A minimal Express server:

const express = require("express");const app = express();app.get("/", (req, res) => res.send("hi from Cloud Run"));app.listen(process.env.PORT || 8080);

Plus a two-line Dockerfile (FROM node:20-slim, copy, npm install, CMD ["node","server.js"]). Pulumi's docker provider builds this for you during up — no separate build step.

Why the order is automatic · the dependency graph

Pulumi builds a directed graph from the way outputs feed into inputs, then walks it — creating independent resources in parallel and dependent ones in order. For our example the graph is:

  I -- "image.imageName" --> S["Service

Change only the Node code, and re-running up rebuilds the image, sees its new digest differs, updates the service, and leaves the repository and IAM grant untouched — the minimal diff, again.

In the freeat project · how Pulumi.stg.yaml is used

Your ~/freeat/pulumi folder holds one program (index.ts) and one config file per stack: Pulumi.stg.yaml for staging, Pulumi.prod.yaml for production. The program is identical for both — only the config file changes. Pulumi.yaml (no stack suffix) just names the project (freeat) and its runtime. This is where a Laravel .env becomes Pulumi config. Click any line:

config: gcp:project: freeat-staging freeat:env: APP_URL: https://freeat-stg-...run.app LOG_CHANNEL: stderr APP_KEY: secure: AAABAMiLE7B38ykLHaiX… DB_PASSWORD: secure: AAABAAe4vh/HJYyb…

Click any line of config

This file is pure input — no logic. index.ts reads gcp:project to know where to deploy, and the whole freeat:env object to fill the container's environment. Secrets sit here encrypted, which is what makes it safe to commit to git.
How index.ts consumes it

One line reads the object; one loop turns every entry into a Cloud Run environment variable:

const config = new pulumi.Config();const envConfig = config.getObject<Record<string,string>>("env") || {};// ...inside the Cloud Run container definition:envs: [ ...Object.entries(envConfig).map(([name, value]) => ({ name, value })) ]

So adding a variable to Pulumi.stg.yaml and running pulumi up is all it takes to give the staging backend a new env var — no code change. Note some values (DB_HOST, DB_PASSWORD, the bucket name) are set dynamically in index.ts from the live resources Pulumi creates, so they can never drift out of sync with the real database or bucket.

Where state & secrets live · pulumi login

Two things must survive between runs: the state (what Pulumi has already created) and the encryption key for those secure: values. Both live in a backend. pulumi login picks and authenticates that backend; pulumi whoami just reports whether you're logged in — the exact check deploy-cloudrun.sh runs before it deploys.

Pulumi Cloud (default)

pulumi login → app.pulumi.com. State and secret-encryption are managed for you; your account is what grants decryption.

Self-managed bucket

pulumi login gs://my-bucket (or s3://…). The state JSON lives in your own cloud storage; secrets are protected by a passphrase.

Local files

pulumi login --local → state under ~/.pulumi. Secrets use a passphrase from PULUMI_CONFIG_PASSPHRASE.

Why the deploy script checks login first

Reading pulumi stack output and decrypting Pulumi.stg.yaml's secrets both need the backend — so the script guards it before doing anything:

if ! pulumi whoami >/dev/null 2>&1; then # not logged in → pulumi loginfi

With a self-managed or local backend you'd also need the right passphrase in the environment, or the secure: values can't be decrypted and pulumi up fails.

The real deploy · what deploy-cloudrun.sh stg|prod does

Here's the important twist versus the toy example above: in freeat, Pulumi provisions the infrastructure — Artifact Registry, a storage bucket, Cloud SQL, a service account with IAM, and the Cloud Run service — but the container image is built and pushed outside Pulumi by this script, then gcloud run deploy rolls it out. Pulumi stays the single source of truth for names and config; the script asks for them with stack output.

  participant Run as Cloud Run
  S->>P: pulumi whoami (login if needed)
  S->>G: gcloud auth check
  S->>P: stack output --json (stg or prod)
  P-->>S: dockerRepoUrl, service, project, region
  S->>G: gcloud auth configure-docker

  S->>Run: gcloud run deploy service --image :latest

The script never hard-codes a project, repo or service name — every one comes from a Pulumi export in index.ts. Change the infra in Pulumi, and this same script automatically deploys against the new values.
Why build the image outside Pulumi?

Pulumi can build images (the toy example used docker.Image), but building in a plain shell script with podman iterates faster and keeps pulumi up about infrastructure, not app builds. The Cloud Run resource in index.ts just points at backend:latest, so a gcloud run deploy of a fresh :latest and a later pulumi up agree — no drift.

Pulumi state is the source of truth about what exists; your program is the source of truth about what should exist. Every run reconciles the two. Code, diagrams and resource names here are illustrative but valid Pulumi.
