Server-Sent Events — how it actually works

One long-lived HTTP response the server never closes. The server pushes text frames down it; the browser's EventSource parses them into events. No polling, no WebSocket upgrade — just Content-Type: text/event-stream. Click any message arrow below for the TypeScript that sends or handles it. Then run the upload demo on the right.

The shape of SSE: the upload returns at once; the events request opens a stream the server keeps writing to; the processor generates the pushes. Below: the exact bytes on the wire.

The wire — what the server literally writes

HTTP/1.1 200 OK Content-Type: text/event-stream Cache-Control: no-cache Connection: keep-alive ← blank line ends headers, body stays open forever ↓ : ok — a comment line (starts with ':'), keeps proxies from timing out event: progress ← es.addEventListener("progress", …); omit ⇒ "message" id: 3 ← browser remembers it; resends as Last-Event-ID on reconnect data: {"step":"transcode","pct":60} ← a blank line terminates the event. THE BLANK LINE IS THE DELIMITER. retry: 3000 ← optional: tell the browser to wait 3s before auto-reconnecting
Why SSE and not polling or WebSocket?

vs polling: polling reopens a request every N seconds and mostly gets "nothing new". SSE is one connection; the server speaks the instant there's news — lower latency, far less overhead.

vs WebSocket: WebSocket is a protocol upgrade giving you a full-duplex binary socket. SSE is just an HTTP response — it rides existing infra (HTTP/2, proxies, auth cookies, gzip), auto-reconnects for free, and carries a built-in event-id/resume mechanism. The catch: SSE is server→client only and text only. If the client needs to stream up too, use WebSocket. For "server tells client about progress", SSE is the lazy correct choice.

The one footgun: over HTTP/1.1 a browser allows only ~6 connections per origin, and each open EventSource burns one. HTTP/2 multiplexes them away. ponytail: fine for one stream per tab; reach for HTTP/2 if you open many.
